# 架构与扩展

## 一次动作如何改变游戏

React 发送一个 `Action`，`gameReducer(previous, action)` 先校验合法阶段，再复制状态并结算。返回的状态包含棋子位置、财产、当前阶段与日志。React 的定时器只负责安排下一次 `STEP` 或电脑动作，不直接扣款或修改地产。

```text
ready → ROLL → moving → STEP ... → purchase / upgrade / shop / end
purchase → BUY / PASS → end
upgrade → UPGRADE / PASS → end
shop → SHOP_BUY（可多次，最多 8 张）/ PASS → end
end → END → 下一位的 ready / over
```

`STEP` 每次只移动一格，经过起点时立即发奖。最后一步到达后才触发落地事件。这保证多步动画、过圈奖励、刷新继续共享同一套规则。

## 随机数与重放

游戏把 32 位随机种子放在 `GameState.seed` 中。骰子、机会事件与每日股价使用同一个线性同余生成器，因此初始状态和动作序列相同，结果就相同。随机种子来自开局时的 `crypto.getRandomValues`；这只是单机体验与测试的可复现性设计，不具备联网竞技所需的防作弊能力。

## 金额与资产

货币使用整数，利息与租金明确取整。规则引擎拒绝负向透支、非整数输入、非法目标和错误阶段。地产价值为买价加已支付的升级造价；出售按该价值的 70% 回收。建房卡免费升级后，也提高地产的账面价值。

自动支付按“现金 → 存款 → 股票 → 地产”处理。股票按当前价卖出，地产从价值较低的开始出售。收租者只收到实际支付的资金，不凭空补足破产者的欠款。支付后立即检查是否只剩一位玩家。

## 电脑为什么不会卡住

`computerAction(state)` 对每个需要决策的阶段返回一个合法动作。每回合只用一张卡片，防止连续用牌；商店达到数量或储备边界后离开。测试把所有四位玩家都交给同一动作函数，运行 80 个种子的完整对局，检测无动作、无变化和超过步数上限。

电脑目前会买地、升级、购买和使用卡片；不会主动做股票交易或手动存取款。三位电脑使用同一策略框架，按角色现金储备参数表现出不同风格。

## 存档与界面

`storage.ts` 在渲染前校验存档版本、地块静态配置、玩家资金、卡片、股数、阶段和移动状态。损坏或不兼容的存档会回到新局界面。浏览器拒绝存储时，游戏继续运行，并提示无法自动存档。

`Board.tsx` 使用等距投影：`screenX = 500 + (x − y) × 43`，`screenY = 130 + (x + y) × 24`。地块和建筑按深度绘制，角色通过 CSS 变换平滑移动。SVG 保持轻量与可读性，不需要 WebGL、贴图下载或原作资源。交互地块提供可访问名称、键盘焦点与 Enter / 空格选择。

## 可以继续改的地方

- `data.ts`：新地图、卡片价格与经济参数；修改静态地图后同时提升存档版本。
- `strategy.ts`：5–10 行即可改变电脑买地风格。
- `engine.ts`：新事件或道具规则，先补对应输入、边界与资金守恒测试。
- `Board.tsx`：新增原创建筑与装饰；不要把闭源游戏素材直接混入 MIT 仓库。

当前版本包含一张地图、四张卡、三支虚构股票和简单电脑策略。未实现原作全部地图、角色技能、神明、载具、小游戏、原版音画、局域网或在线多人。
